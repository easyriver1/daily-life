# 一万条数据查一行很快，一亿条就卡死：索引到底做了什么

一个表格，一万行，按某个字段查一行，眨眼就好。

把同样的表扩到一亿行，同样一句查询——**跑了四十秒还没出结果。**

数据只多了一万倍，时间却慢了几万倍。这不是硬件不行，是**查询方式**没变。

这篇讲清楚索引做了什么，以及为什么加了它就快。

---

## 先看没有索引时发生了什么

假设一张用户表，一亿行，你要找 `id = 88776655` 这一行。

数据库没有别的信息，只能**从头一行一行看**，看到第 8877 万行才找到。

这叫全表扫描。它的代价是：**数据翻倍，时间也翻倍。**

一亿行就是看一亿次。哪怕每次只要一微秒，也要 100 秒。

问题不在"看得慢"，在于**它必须看完全部**。

---

## 索引：多维护一本目录

现在换个做法：额外维护一个结构，按 `id` 排好序，每一项记着"这个 id 在表格的哪个位置"。

再查 88776655 时，不用从头看——**在这本有序目录里找**。

有序的东西可以二分：一亿项，最多 27 次就定位到了。

27 次 vs 一亿次。

这就是《什么是算法》那篇讲的道理：**同样的数据，换个找法，量级完全不同。**

---

## 但索引不是"排好序的数组"

如果索引真的只是一个排序数组，它有个致命问题：**插入很贵。**

一亿个元素的数组，中间插一个，后面所有元素都要往后挪。表里每加一行，就要挪几千万次，那写入就废了。

所以数据库用的是一种能"边插边保持有序"的结构——**B+ 树**。

你不需要记它的细节，只需要知道它满足两件事：

1. **找得快**：几层就定位到，一亿行的树高度通常只有 3–4 层
2. **插得也不慢**：插入只影响一小块，不用整体挪动

代价是多占一些空间，以及每次读写都要维护这个结构。

---

## 所以索引的代价是真实的

新手最容易犯的错，是"能加索引的地方都加上"。

它的成本有三块：

| 成本 | 说明 |
|---|---|
| **占空间** | 索引本身也是数据，通常占表的 10%–30% |
| **写入变慢** | 每插一行，所有相关索引都要更新 |
| **可能没用** | 查询条件用不上这个索引时，它只带来成本 |

第三条最隐蔽。**索引不是"加了就快"，是"查询刚好能用上它才快"。**

---

## 一个常见误区：给"性别"加索引

假设一列只有两种值：男 / 女。

给它加索引，效果接近于零——因为你查"男"，结果是一亿行里的五千万行。**数据库一看要返回一半的数据，还不如直接全表扫。**

判断标准叫选择性：**这一列能区分出多少种不同的值。**

- 手机号、身份证号：几乎每行都不同 → 选择性极高 → 适合索引
- 性别、是否删除：只有两三种值 → 选择性极低 → 不适合

---

## 联合索引为什么有"顺序"

如果你经常按 `(城市, 年龄)` 一起查，可以建一个联合索引。

但它有个规则叫最左前缀：**这个索引能用于"城市"、能用于"城市 + 年龄"，但不能单独用于"年龄"。**

原因还是排序：它先按城市排，城市相同再按年龄排。你只给年龄，就没法用这个顺序。

**类比：电话簿按"姓 + 名"排。你能快速找到"张"开头的所有人，也能找到"张三"，但没法快速找"所有名叫三的人"。**

---

## 一条边界

索引解决的是"找得快"，不解决"数据太多"。

如果一张表真的到了一亿行，光加索引往往不够——还要考虑分表、归档、只保留近期数据。**索引是让查询变快，不是让数据变少。**

另外，索引对写入密集的系统是负担。**读多写少的表适合多加，写多读少的表要克制。**

---

## 你现在可以验证

如果你装过 MySQL 或 SQLite，用 `EXPLAIN` 看一条查询的执行计划：

```sql
EXPLAIN SELECT * FROM users WHERE id = 88776655;
```

加索引前，输出里的 `type` 通常是 `ALL`（全表扫）；加了索引之后再跑一次，会变成 `ref` 或 `const`（走索引）。

**这一行输出，就是"快"和"慢"的全部区别。**
