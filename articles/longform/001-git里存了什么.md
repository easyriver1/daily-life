# git 里到底存了什么：一次提交之后，磁盘上多了什么

你先是想知道「git 是干嘛的」，然后是「git 命令怎么用」，再然后大概会卡在一个地方：**它为什么这么奇怪。**

为什么提交过一次的东西就改不了？为什么切换分支这么快？为什么 rebase 之后每个提交的编号都变了？为什么同样一份代码存了一百个版本，仓库还是只有几十兆？

这些问题的答案在同一个地方：`.git` 目录。打开它看一眼，git 就不神秘了。

---

## 一、先纠正一个直觉：git 不是网盘

大多数人对版本控制的第一印象是「存旧版本」——像网盘的历史记录。这个理解会让你永远看不懂 git。

git 的底层其实是一个**内容寻址的文件系统**（content-addressable filesystem）。这个说法来自 Pro Git 第 10 章的第一句话，值得逐字读一遍。

什么叫内容寻址？普通的文件系统是「按名字找内容」：你说 `笔记.txt`，它去找这个名字对应的东西。git 反过来：**它按内容算出一个名字**。

你对一段文件内容做一次 SHA-1 计算，会得到一串 40 位的十六进制字符，长得像这样：

```
8d0e41234f24b0b3ee86960f0d2aa76c5e1b0e3f
```

git 用它当文件名。也就是说——**内容决定了名字，名字里包含着内容**。

这个设计带来一个直接后果：只要内容一个字都没变，算出来的名字就一模一样，git 就没必要存第二份。所以你在 git 里存同一个文件一百次、每次只改一行，它实际存的是一百份「差异 + 一份完整的公共部分」。

这也是为什么仓库不会膨胀到你想象的程度。

---

## 二、`.git/objects` 里到底躺了什么

提交一次之后，`.git/objects` 下会多出几个以两位十六进制命名的文件夹，里面是压缩过的二进制文件。这些东西叫**对象**，一共三类：

| 对象 | 存什么 | 类比 |
|---|---|---|
| **blob** | 一个文件的完整内容（不含文件名） | 一份稿纸 |
| **tree** | 一个目录：里面有哪些文件名、各自指向哪个 blob | 一个文件夹的清单 |
| **commit** | 一个快照：指向一个 tree、指向父提交、作者、时间、提交说明 | 一张照片的背面写着「这是哪一天、跟上一张什么关系」 |

注意第一行那个细节：**blob 里没有文件名**。

这是 git 设计里最反直觉的地方之一。同样一段内容，你叫它 `a.txt` 还是 `b.txt`，存下来的 blob 完全一样——文件名不归 blob 管，归 tree 管。

所以「重命名文件」在 git 眼里根本不是一次操作。你只是改了一个 tree 里某一行指向的名字，内容对象一个都没动。这就是为什么 `git mv` 那么快，也是为什么 git 需要「猜」你是不是重命名（它靠内容相似度反推）。

---

## 三、`git add` 和 `git commit` 各做了哪一半

把一次提交拆开看，动作是两段：

**第一段，`git add`**：把你工作区里文件的当前内容，算一个哈希，写成 blob，放进 `.git/objects`。此刻文件已经进了 git 的仓库，但还没有「历史」。

**第二段，`git commit`**：根据暂存区里的文件名与 blob 对应关系，生成一个 tree 对象；再生成一个 commit 对象，指向这个 tree。

commit 对象里存的东西大致是：

- 指向哪个 tree（这次提交的完整目录快照）
- 父提交是谁（`parent` 字段；第一次提交没有）
- 作者、提交时间
- 提交说明（那句话）

写完，git 把这个 commit 的哈希写进 `refs/heads/main` 这个文件。**提交就完成了。**

这就是全部。没有「增量记录」，没有「差异数据库」。每一次提交，都是一个**完整快照**——只不过因为相同内容只存一份，完整快照并不占那么多空间。

---

## 四、分支：只是一个写着哈希的文本文件

这一点如果早一点知道，git 的很多命令会立刻变得直观。

`.git/refs/heads/main` 是一个**普通的文本文件**，内容只有一行：

```
6c9e72d3a1b8f0e5c2d9a7b4e6f8c1d3a5b7e9f1
```

这就是 `main` 分支的全部内容。一个指向某个 commit 的四十位哈希。

所以：

- **「创建分支」** = 新建一个文件，写进当前 commit 的哈希。一毫秒完成，因为真的只是写个文件。
- **「切换分支」** = 换一个文件去读，再把工作区里的文件按那个 tree 摆好。
- **「合并分支」**（快进合并）= 把 `main` 那个文件的内容改成另一个分支的哈希。**没有任何文件被复制。**

这也解释了一个曾经让我困惑的现象：为什么在空仓库里切分支是「瞬间」的，而在一个几十万文件的仓库里也是瞬间的——因为它改的是一个文本文件，不是几十万个文件。

（真正的合并当然不止这样。当两个分支都往前走了，git 必须找出共同的祖先、比较各自的 tree、生成一个新的合并提交。但即便是这一步，它比较的也是 tree 与 blob 的哈希，不是逐个字节读文件。）

## 五、哈希带来的三个「怪现象」

**怪现象一：为什么提交过的东西改不了？**

因为提交的名字就是它内容的哈希。你「修改一个提交」意味着内容变了、哈希变了——**它已经不是原来那个提交了，而是一个新的提交**。git 不允许你改，物理上就改不了。

所谓 `git commit --amend`、`git rebase`，做的都是「丢掉旧的、生成新的」，旧对象暂时还在磁盘上，直到被垃圾回收。

**怪现象二：为什么 rebase 之后所有提交编号都变了？**

因为 rebase 的本质是「把这些改动重新应用一遍到新的基点上」，每应用一次就是**生成一个新的 commit 对象**。新对象的父提交变了，内容里的 `parent` 字段变了，哈希自然全变。它不是「移动」提交，是「重做」提交。

**怪现象三：为什么 git 能那么快判断出你改了哪些文件？**

因为它不需要读文件内容。它把你的工作区文件重新算一遍哈希，和暂存区 tree 里记录的哈希比一比，对不上就是改了。你在一个几万文件的仓库里执行 `git status` 一秒出结果，靠的是这个。

## 六、那知道这些有什么用

不是为了炫技。是三个具体的实用价值：

**第一，很多「git 坏了」的恐慌会消失。** 提交「丢」了，往往只是没有分支指向它——它还在对象库里。`git reflog` 能看到它，`git reset` 能回去。知道对象不会凭空蒸发，你就敢动手试。

**第二，你会理解为什么有些操作危险。** `git reset --hard` 会让分支指针后退，而它「丢掉」的提交如果没有任何分支或标签指着，就只剩 reflog 这根线。这就是为什么老手在大操作前都会先 `git branch backup`——**建一个分支的成本是一个文件**，贵不到哪去。

**第三，也是最重要的：你能看懂报错。** git 的报错习惯原文使用这些词：`tree`、`object`、`dangling`、`unreachable`。不理解对象模型，这些词就是天书；理解了，报错等于在告诉你「仓库里的数据结构出了什么状况」。

---

## 最后

回头看你第一天学会的 git 命令——`add`、`commit`、`branch`、`merge`——它们全都是对三个对象的操作：

- `add` 写 blob
- `commit` 写 tree 和 commit
- `branch` 写一个文本文件
- `merge` 找一个更好的指向方式

命令是壳，对象是里子。壳会忘，里子不会。

下一篇如果讲分支与合并，我会拿这个模型解释「三个人改同一份文件为什么最后不会互相覆盖」——那件事在这个模型下是显然的，在「网盘」模型下是魔术。
